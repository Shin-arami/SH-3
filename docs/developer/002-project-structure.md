# 1. Purpose

This document defines the canonical project structure for SH-3.

A standardized project structure ensures:

- Consistent development
- Predictable component locations
- Clear architectural boundaries
- Simplified maintenance
- Automated tooling support
- Long-term scalability

All SH-3 projects generated by the DevKit shall conform to this specification.

---

# 2. Design Principles

The project structure follows the core SH-3 principles:

- Everything Event Driven
- Everything Replaceable
- Everything Typed
- Everything Testable
- Everything Documented

Each directory has a single architectural responsibility.

---

# 4. Layer Responsibilities

## foundation/

Provides reusable primitives.

Contains:

- Types
- Constants
- Exceptions
- Utilities
- Protocols
- Base Classes

Rules:

- No business logic
- No service dependencies
- No runtime state

---

## infrastructure/

Provides technical capabilities.

Contains:

- Logging
- Metrics
- Tracing
- Storage adapters
- Serialization
- Networking

Infrastructure depends only on Foundation.

---

## runtime/

Provides execution capabilities.

Contains:

- Scheduler
- Event loop
- Context
- Lifecycle
- Executor

Runtime must not contain business logic.

---

## services/

Implements domain services.

Examples:

- Memory
- Learning
- Planning
- Security
- Policy

Services coordinate behavior but remain replaceable.

---

## kernel/

Coordinates the framework.

Contains:

- Registry
- Event Bus
- Pipeline
- Component Manager
- Dependency Resolver

Kernel is the orchestration layer.

---

## persistence/

Responsible for:

- Snapshot
- Repository
- Storage abstraction
- Recovery state

---

## self_healing/

Provides:

- Health monitoring
- Failure detection
- Recovery
- Repair
- Diagnostics

Directories:

snake_case

Python packages:

snake_case

Classes:

PascalCase

Functions:

snake_case

Constants:

UPPER_CASE

# 12. File Organization

One primary class per module is recommended.

Avoid files exceeding approximately 500 logical lines unless justified by cohesive functionality.

Related helper functions should remain close to their owning component.

---

# 19. Best Practices

- Keep directories cohesive.
- Avoid cyclic dependencies.
- Keep public APIs stable.
- Document every public package.
- Mirror tests to implementation.
- Separate generated artifacts from source.

---

# 20. Anti-Patterns

Avoid:

- Mixing architectural layers.
- Placing business logic in Runtime.
- Direct cross-layer shortcuts.
- Shared mutable globals.
- Circular imports.
- Unversioned documentation.

---

# 21. Validation Checklist

A project structure is compliant when:

- Directory layout matches the specification.
- Dependency direction is preserved.
- Naming conventions are followed.
- Tests mirror source layout.
- Documentation is complete.
- Generated artifacts are isolated.

---

# 22. Final Definition

The SH-3 project structure provides a predictable, scalable, and maintainable foundation for implementing production-grade AI operating systems while preserving architectural integrity.
