# 2. General Questions

## Q: What is SH-3?

SH-3 is a modular, event-driven AI Operating Framework designed around the principles of:

- Everything Event Driven
- Everything Replaceable
- Everything Typed
- Everything Testable

---

## Q: Which Python version is required?

Python 3.12 or later.

Older versions are not officially supported.

---

## Q: Which formatter should I use?

Use Ruff Formatter.

Formatting should not be performed manually unless necessary.

---

# 3. Architecture

## Q: Why is SH-3 event-driven?

Events reduce coupling between components.

Benefits include:

- Replaceability
- Scalability
- Observability
- Easier testing

---

## Q: When should components communicate directly?

Only when:

- Immediate synchronous results are required.
- Event-based communication provides no architectural benefit.

Otherwise, prefer events.

---

## Q: Why are Protocols preferred?

Protocols provide interface-based design without requiring inheritance.

They improve:

- Dependency injection
- Testability
- Replaceability

---

## Q: When should Abstract Base Classes be used?

Use ABCs only when:

- Shared implementation exists.
- Lifecycle behavior is centralized.

Otherwise, use Protocol.

---

# 4. Components

## Q: How large should a component be?

Components should have one primary responsibility.

Large responsibilities should be divided into multiple components.

---

## Q: Should components create dependencies internally?

No.

Dependencies should be injected through constructors.

---

## Q: Can components share mutable state?

Avoid shared mutable state whenever possible.

Prefer immutable models and explicit synchronization.

---

# 5. Events

## Q: What should an event represent?

An event represents something that has already happened.

Examples:

- PluginRegistered
- MemoryUpdated
- ComponentStarted

Avoid command-style event names.

---

## Q: Should event payloads use dictionaries?

No.

Use dedicated typed models.

---

## Q: Can events change after publication?

No.

Events should remain immutable.

---

# 6. Plugins

## Q: How are plugins discovered?

Through the Plugin Registry.

Discovery and registration occur during initialization.

---

## Q: Can plugins modify SH-3 core modules?

No.

Plugins extend behavior without modifying the framework.

---

## Q: Are plugins versioned?

Yes.

Plugins should declare compatibility and semantic versions.

---

# 7. DevKit

## Q: How do I create a component?

Example:

```bash
sh3dev component create Planner
```

---

## Q: How do I validate my project?

```bash
sh3dev validate
```

---

## Q: How do I build documentation?

```bash
sh3dev docs build
```

---

# 8. Testing

## Q: What tests are required?

Every public component should include:

- Unit tests
- Integration tests

Critical functionality should additionally include:

- Performance tests
- Security tests

---

## Q: What coverage is recommended?

Recommended minimums:

- Line coverage ≥ 90%
- Branch coverage ≥ 80%

---

# 9. Performance

## Q: Should I optimize immediately?

No.

Measure first.

Optimize only after identifying actual bottlenecks.

---

## Q: Is caching always recommended?

No.

Introduce caching only when measurements justify the additional complexity.

---

# 10. Security

## Q: Where should secrets be stored?

Outside the source tree.

Use environment variables or a secure secret provider.

---

## Q: Should authentication logic be mixed with business logic?

No.

Authentication and authorization should remain separate concerns.

---

# 11. Releases

## Q: How are versions managed?

SH-3 follows Semantic Versioning.

Examples:

```
1.0.0
1.1.0
2.0.0
```

---

## Q: When is an RFC required?

Typically for:

- New architecture
- Breaking changes
- Cross-layer features
- Public API evolution

---

# 12. Documentation

## Q: When should documentation be updated?

Whenever:

- Public APIs change
- Architecture changes
- Configuration changes
- User-visible behavior changes

Documentation should remain synchronized with implementation.

# 13. Troubleshooting

## Q: Validation fails. What should I check?

Verify:

- Ruff
- MyPy
- Tests
- Configuration
- Project structure

---

## Q: An event is not handled.

Check:

- Event registration
- Subscriber registration
- Event Bus routing
- Event filtering
- Logs

---

## Q: A plugin is not loaded.

Verify:

- Manifest
- Compatibility
- Registration
- Configuration
- Logs
